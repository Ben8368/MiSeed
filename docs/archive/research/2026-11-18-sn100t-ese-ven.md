# Umi SN100T：eSE 回调与共享 VEN 的证据边界（WP10）

2026-11-18｜工作树基线 `fe9c0ba`。结论：保留 NFC-only transport，不注册虚拟 eSE、不补空回调，不改 VEN 策略。正常 eSE 通路与硬件复位是两项独立审查；前者不应以允许复位为前提。本轮不操作手机。

## 芯片能力、板级连线和时间依据

- [NXP SN100T 安全目标 §1.2](https://www.commoncriteriaportal.org/files/epfiles/SecurityTarget-Lite_SN100T_v1.1_20190418.pdf)描述受评 eSE 经片内 System Mailbox/HCI 与 NFCC 通信，并描述有线 APDUCard Gate；[SN100 系列安全目标](https://www.commoncriteriaportal.org/nfs/ccpfiles/files/epfiles/NSCIB-CC-2400058-02-ST_lite_v4_3.pdf)说明片内 PMU 共享。这些不是 Umi 主机路由表、VEN 电气规范或本机固件身份证明。
- [锁定 NQ 源码](https://github.com/LineageOS/android_kernel_xiaomi_sm8250/blob/6fcac56423a078c7bd180e8d2c626c7d66bf1677/drivers/nfc/nq-nci.c)：`ESE_SET_PWR` 按芯片类型分派；SN100 A/B 的 `sn100_ese_pwr()` 操作共用 `en_gpio`，另一分支的 `ese_gpio` 不是本机独立电源依据。SN100 分支的软件会话标志与读回 VEN 不是芯片空闲确认；`ESE_COLD_RESET` 是另一条命令路径，不是 VEN 脉冲。旧分支中的延时不作本板最短/最长时限。
- [Android 只读基线](../hardware/2026-11-10-umi-nfc-android-baseline.md)确认 GPIO83 和服务/库身份；`eSE1`、配置 `eSE2` 和 QTEE 库不能区分 AP→NFCC→eSE 与受信侧 SPI 的实际归属。若匹配资料确认 SPI 由安全世界独占，则不把这条路径包装成 Linux NCI eSE。
- [同板 L3](../hardware/2026-11-18-umi-display-nfc-ese-l3.md)：较早镜像 `0x28/W` 地址阶段 NACK；后来仅在 probe 设置 FIRM 前采到 FIRM/VEN=1/1。不是一次同步采样，更没有 FIRM 锁存沿。当前 open 顺序是 FIRM 低且读回 → VEN 高且读回 → 等待 10–15 ms → 启用 IRQ；VEN 本已高时没有已证上升沿。等待仅是现有驱动行为，不证明 NFCC ready 或 eSE 空闲。

## 锁定 Linux 6.18.60：挂回调会改变哪些行为

依据：[NFC core](https://github.com/gregkh/linux/blob/f45ed76d6791cf72ff1265ee93511175bbbc2f18/net/nfc/core.c)、[NCI core](https://github.com/gregkh/linux/blob/f45ed76d6791cf72ff1265ee93511175bbbc2f18/net/nfc/nci/core.c)、[NFCEE 通知](https://github.com/gregkh/linux/blob/f45ed76d6791cf72ff1265ee93511175bbbc2f18/net/nfc/nci/ntf.c)、[NFC netlink](https://github.com/gregkh/linux/blob/f45ed76d6791cf72ff1265ee93511175bbbc2f18/net/nfc/netlink.c)。候选用户态为 Debian NFC generic netlink；不新增 DT 属性、私有 ioctl 或 Android 运行依赖。

| 入口 | 已核实的行为 | 接入前必须证明 |
| --- | --- | --- |
| `discover_se` / `GET_SE` | `GET_SE` 只列已登记元素；在 `nfc_dev_up()` 调用底层 `dev_up` 后，探测不受其返回码守卫，探测失败不改变 DEV_UP 返回码。非空芯片回调会让 NCI 先请求 `NFCEE_DISCOVER`。HCI 网络可代表多个元素，一条通知的 ID 不足以区分 eSE/UICC。 | 用匹配 Umi/固件的传输与身份记录建立映射后才 `nfc_add_se(..., NFC_SE_EMBEDDED)`；零元素、仅 UICC、未知标识均不得登记 eSE。失败 open 后不得再发包；不要用返回 0 或 `-EOPNOTSUPP` 的探测桩。 |
| `enable_se` / `disable_se` | NCI 包装层缺回调可返回 0；NFC core 按回调结果更新已登记元素的状态。 | 对应同一已识别元素的建立/释放确认；区分 RF、主机与受信侧占用，不以 VEN 高低或本地引用数推断外部持有者。 |
| `se_io` / `NFC_CMD_SE_IO` | 请求受 `GENL_ADMIN_PERM` 限制，但 `se_io_cb` 将响应 APDU 发往 NFC 事件组而非请求方单播，且不编码 `err`。回调上下文由完成路径释放；请求 ACK 不是 APDU 响应。 | 产品须能隔离响应，区分失败和合法响应。仅限制发送方或不记日志不够；无法隔离就不开放。异步使用前持有独立请求数据；同一元素只允许一个在途请求，交付、超时、禁用、移除竞争只能完成/释放一次，迟到包不能匹配下一请求。 |
| `DEV_DOWN` / rfkill / remove | `nfc_dev_down()` 检查 polling/active target，不以 SE 在途为门槛，也不传播底层 down 的结果；UP 状态下 `nci_close_device()` 先请求 `CORE_RESET`，再调 transport `.close`。unregister 亦经 `nci_close_device`。 | 任何可能影响 SE 的 reset **之前**阻止新会话、按确证协议排空/取消，且覆盖非本地所有者；不能仅在 `.close` 返回忙。可拒绝的下电与不可拒绝的移除分别处理。 |

若既有路径不足，WP10 先向 Linux NFC/netdev 维护者评审通用的请求方定向完成、可上报的错误与 reset 前仲裁，验证既有 ABI 兼容性；不在 SN100T transport 内另造私有通道或默改组播语义。[上游 ST 实现](https://github.com/gregkh/linux/blob/f45ed76d6791cf72ff1265ee93511175bbbc2f18/drivers/nfc/st-nci/se.c)只参考生命周期，不采用其 host/gate 常量、白名单或超时触发的软硬复位。

## 如何解除阻断（按顺序）

1. **先核身份，不发命令。** 向 NXP/板方取得适用芯片步进、NFCC/SE 固件与板修订的主机接口说明；核对允许的有线路径、HCI host/gate/pipe 的发现方式与外部所有者交接。查不到就停在 NFC-only，不以 Android 实例编号凑 ID。
2. **正常通路不动 VEN。** 首发 NCI 仍须按已有计划独立复验。实现前先以脱敏合成输入验证错误身份、忙、超时/迟到、关闭/移除与权限隔离；再以标准 `GET_SE` 枚举及获授权的非支付测试 applet 单次往返验收，不读生产应用、密钥或记录原始 APDU。真实 eSE 枚举、SE_IO 响应和释放均须单独取证。
3. **只有确实需要硬复位才另开评审。** 必须有匹配的 VEN/FIRM 时序表（采样边沿、建立/保持、脉宽、时钟/电源条件、首笔 I²C 允许时刻）、板级引脚与电平域、所有共享方可验证的空闲/交还信号和故障回退。已知正常启动的同步 SCL/SDA、VEN/FIRM、IRQ 波形只作对照；没有边沿就记“未测”，不以单次样本反推规范或安全上下限。材料、独立复核、本轮授权及回退未齐不得试脉冲；NACK/超时不构成授权。
