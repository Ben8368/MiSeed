# Umi RX1619 只读驱动与 NFC 射频暂停

2026-11-19，RQ-14 / WP12，范围为 Umi 无线接收 RX。宿主 Windows x64 / PowerShell 7.6.9，内核构建经 Ubuntu 24.04 WSL2。板级依据为[本机 LOS 对照](../hardware/2026-11-19-umi-wireless-rx-baseline.md)，主线基线为 Linux `v6.18.60` / `f45ed76d6791cf72ff1265ee93511175bbbc2f18`。

## 固定接口与差异

| 功能 | 固定内核接口 | Debian 用户态 | 本地差异 |
| --- | --- | --- | --- |
| RX 电源状态与输出遥测 | GENI I²C、regmap、PM8150B GPIO7 power-good 双边沿、`power_supply` | `/sys/class/power_supply/rx1619/{online,voltage_now,current_now}` 和 uevent。电压 µV、电流 µA，离座读数返回 `ENODATA` | 锁定内核有 `POWER_SUPPLY_TYPE_WIRELESS`，无 RX1619 驱动或 binding。实现范围为读取状态、VOUT 和 IOUT。 |
| NFC 共存 | 标准 Linux NFC/NCI，RF_DEACTIVATE idle | NFC generic netlink、AF_NFC。新 RF 请求在暂停时返回 `ERFKILL`；离座后应用重新寻卡。 | 固定 NFC rfkill 回调通过 `nfc_dev_down` 下线，活动轮询或目标会拒绝下线，且核心关闭会 CORE_RESET。扩展 NCI 核心，在连接保持时停止射频并清理已结束的发现。平台由标准电源通知驱动。 |
| 有线 SMB5/PPS 互锁 | 同一 USBIN 的独立来源判断、既有 SMB5/PPS 停机与交还流程 | 有线与无线电源对象各自提供状态 | RX 工作时有线策略退出，RX 读错时有线策略拒绝开始或退出。两路同接时采用同一互锁，待本机确认。 |

审查时按 [power_supply 属性](https://docs.kernel.org/power/power_supply_class.html) 和 [DT binding 编写规则](https://docs.kernel.org/devicetree/bindings/writing-schema.html) 检查语义、单位、读写权限与资源生命周期。通用的 NCI 机制与 SN100T/板级策略分别实现，待 Linux NFC 与 Devicetree 子系统评审。P9415 在本机未绑定，不能复用其驱动或 binding。Android 代码与用户态服务只作对照。

## 真机验收范围

下文保留 11 月 19 日的历史计划；其双输入方向已被 [RQ-15](../../PRODUCT.md) 替代。新验收以 [WP12](../../implementation-plan.md) 为准：屏蔽无线 RX，保留有线；见[只读对照准备](../hardware/2026-11-19-umi-wireless-rx-baseline.md#2026-11-20有线优先的只读对照准备未接机)。

1. 底座离座、无手机 USB-C。比较 Linux `online`、RX 输出单位、与 LOS 上座／移除数据，核查错误及恢复事件。
2. NFC 寻卡与已选卡分别验证。上座核实 NCI idle 完成和后续请求被拒绝，离座重试寻卡。覆盖开机已在底座、离座时用户保持 NFC 关闭、读错恢复和 suspend/resume。共享 VEN 不作为恢复动作，eSE 另验。
3. 无线底座与实体 USB 插头都存在时，分别核对有线 SMB5 与 PPS 退出、回到单独有线后恢复。主动 RX 前补采 PMIC 实际路径和电池净电流，按风险条目验证保护。设备操作待单独准备与授权。

## 同次启动 RX/NFC 验证准备

默认 Umi/CSOT 诊断镜像加入 `rx-nfc-poll` 与 `rx-nfc-target`。每次 RAM 启动选一项，分别验证在途轮询或已选中目标。探针在 USB 断开后继续运行，将 RX 边沿、`ERFKILL`、NCI 已确认的 RF idle 和离座重新发现记录到同一 RAM 日志。电池电流与 SMB5 `POWER_PATH_STATUS` 同窗导出，保留原始读数和有效位。先执行 `poll`，`target` 在同一台手机上另做一次独立 RAM 启动。主动 RX 供电和两种输入同时接入的策略另验。

- 本地包位于 `.work/umi-rx-nfc-l3-20261119/`。`boot.img` SHA-256 为 `c3ebf7ba8c63f6d8a7c11337b0754a3aaa38e1ee354660d898a7d77cc479e69b`。默认配置 L2 与定向 DT 验证通过，镜像内 DTB 与包内 DTB 的哈希一致。Windows `python -X utf8 .work/umi-rx-nfc-l3-20261119/run.py --check` 通过，核实了镜像、构建输入锁、配置和既有 ADB/Fastboot 工具哈希。
- WSL `python3 -m unittest discover -s tests -q` 通过，322 项中跳过 4 项，RX/NFC 专项 3 项均运行。Windows 的 RX/NFC 专项 2 项通过，Linux C 桩跳过。Windows 模拟单次启动、采集失败留档和正常 Android 回退路径，均满足预期。
- 接机时使用已解锁的 `umi`、现有无线底座、USB 数据线及一张实体 MIFARE 测试卡。手机先离座，`poll` 模式的测试卡先移开。收到 `READY` 后物理拔除手机 USB‑C，离座约 5 秒，放上底座约 20 秒，取下后把测试卡贴近手机约 25 秒，再接回 USB 导出。`target` 在启动 probe 前把卡贴稳，移座过程中保持位置。
- FDT 硬件或 RAM 校验失败、探针超时、提前接回 USB、射频未按预期停启或日志缺失时保留当次记录。验证结束后经已识别的救援控制台正常重启，或经身份复核后的 Fastboot 返回 Android。若 USB 失联且无法确认接口，结束自动命令，待操作者恢复正常启动。
- [首轮 RAM 记录](../hardware/2026-11-19-umi-rx-nfc-ram-poll.md)：在等待拔线时回退到 Android。主持脚本现先等操作者确认就绪，再发送实际探针命令。

## 第二轮后复测顺序

复核 [恢复日志](../hardware/2026-11-19-umi-rx-nfc-ram-poll.md#第二轮拔线上座与离座)：电脑 USB 连接窗口 8 组、上座窗口 7 组，当前驱动均报告 `pm8150b-charger/online=1`、`usb_type=Unknown`、`rx1619/online=0`。两段的 PMIC 实际路径读数不同。现有 `smb5_get_prop_usb_online()` 看到 `USBIN_PLUGIN` 且 RX 离线就报告有线在线，能解释上座时有线策略仍可能运行。

1. 构建单独的 RX 取证 RAM 镜像，启动时保持 SMB5 电池充电和 BQ25970 泵关闭，保留 USB 数据和只读日志。让 Type‑C 物理连接与 RX 状态分别取证。固定主线 Qualcomm Type‑C 驱动读取 PM8150B `CC_ATTACHED`，TCPM 通过标准 Type‑C class 发布 `portN-partner`。先核实仅接电脑时的拔插边沿，用主机 USB 枚举互证。状态不一致时结束该轮并保存日志。 [Linux Type‑C ABI](https://docs.kernel.org/driver-api/usb/typec.html)
2. 连接判据通过后，按离座、上座、移除取同步读数。对照 LOS 的 TLMM GPIO155（RX enable）、PM8150B GPIO7（power-good）、RX1619 遥测、PMIC 选路和带方向的电池电流。LOS active pinctrl 包含 `GPIO155 output-low`，现有 MiSeed RX 节点只声明 power-good。先对照实机状态并核定用途和时序，再决定驱动是否需要接管 enable。 [锁定板级接线](https://github.com/LineageOS/android_kernel_xiaomi_sm8250/blob/71b13e62f057a649b77fe4062feb73ee72ad609c/arch/arm64/boot/dts/vendor/qcom/umi-sm8250.dtsi#L132-L145)
3. 独立验有线互锁。没有有效的物理 USB 输入、输入归属不明或读回失败时，SMB5/BQ 有线充电禁止启用。复核普通 USB、固定 PD、PPS 的插拔恢复。RX 上座边沿得到确认后，恢复 NFC 同次启动验证。主动 RX 供电继续由 [RISK-013](../../RISK_REGISTER.md) 约束。
